# TVLift Controller

# Project Vision

**Версия документа:** 1.0

**Статус:** Draft

**Дата:** 2026-07-20

---

# 1. Назначение проекта

TVLift Controller — это интеллектуальный контроллер управления механизмом подъема и опускания телевизора, построенный на базе микроконтроллера ESP32.

Устройство предназначено для управления электрическими приводами телевизионных лифтов, мебели с автоматическим открыванием, подъемных механизмов и других электромеханических систем.

Проект ориентирован не на создание единичного устройства, а на разработку масштабируемой платформы, которая может использоваться в нескольких линейках изделий.

---

# 2. Цели проекта

Основные цели разработки:

- создать надежную промышленную прошивку;
- обеспечить возможность удаленного обновления программного обеспечения;
- максимально упростить первоначальную настройку устройства;
- обеспечить высокую отказоустойчивость;
- сделать архитектуру независимой от конкретной аппаратной ревизии;
- обеспечить возможность дальнейшего расширения функциональности без переписывания существующего кода.

---

# 3. Основные требования

Контроллер должен:

- работать круглосуточно без перезагрузок;
- автоматически восстанавливать работу после отключения питания;
- автоматически восстанавливать соединение с сетью;
- поддерживать безопасное обновление прошивки;
- сохранять пользовательские настройки;
- иметь встроенные средства диагностики.

---

# 4. Основные возможности

Первая версия должна поддерживать:

- Wi-Fi;
- Ethernet;
- первоначальную настройку через Captive Portal;
- REST API;
- удаленное обновление прошивки (OTA);
- управление приводом;
- хранение конфигурации;
- журнал событий;
- удаленную диагностику.

---

# 5. Требования к надежности

Контроллер является частью исполнительного механизма.

Ошибки программного обеспечения могут привести к:

- остановке механизма;
- повреждению оборудования;
- ухудшению пользовательского опыта.

Поэтому:

- никакая ошибка не должна приводить к повреждению оборудования;
- после любой программной ошибки устройство должно автоматически восстанавливаться;
- критические ошибки должны фиксироваться в журнале.

---

# 6. Безопасность

Контроллер обязан обеспечивать безопасную работу оборудования.

Запрещается:

- одновременное включение противоположных направлений двигателя;
- выполнение потенциально опасных команд при обнаружении ошибок;
- установка неподписанной или поврежденной прошивки.

Все сетевые соединения должны использовать защищенные механизмы передачи данных.

---

# 7. Производительность

Контроллер должен:

- быстро загружаться после подачи питания;
- обеспечивать мгновенную реакцию на команды управления;
- выполнять сетевые операции в фоновом режиме;
- не блокировать управление механизмом во время работы сети или OTA.

---

# 8. Масштабируемость

Архитектура должна позволять без существенных изменений добавлять:

- новые аппаратные ревизии;
- новые исполнительные механизмы;
- новые интерфейсы связи;
- новые мобильные приложения;
- облачные сервисы;
- дополнительные датчики.

---

# 9. Поддерживаемые интерфейсы

На первом этапе предусматривается поддержка:

- Wi-Fi IEEE 802.11 b/g/n;
- Ethernet;
- UART (Universal Asynchronous Receiver/Transmitter);
- I²C (Inter-Integrated Circuit);
- SPI (Serial Peripheral Interface);
- CAN (Controller Area Network);
- инфракрасного приемника;
- инфракрасного передатчика.

Архитектура должна позволять подключение дополнительных интерфейсов без изменения существующей логики.

---

# 10. Архитектурные принципы

Проект разрабатывается в соответствии со следующими принципами:

- модульность;
- слабая связанность компонентов;
- высокая читаемость кода;
- единый стиль разработки;
- разделение аппаратной и прикладной логики;
- отсутствие скрытых зависимостей между модулями;
- документирование всех публичных интерфейсов.

---

# 11. Принципы разработки

Каждый новый модуль должен:

- иметь четко определенную ответственность;
- иметь минимальное количество зависимостей;
- иметь документированный интерфейс;
- быть пригодным для повторного использования;
- быть максимально независимым от остальных компонентов системы.

---

# 12. Принципы тестирования

Перед включением в основную ветку проекта каждый модуль должен пройти:

- модульное тестирование;
- интеграционное тестирование;
- тестирование на реальном оборудовании.

---

# 13. Поддерживаемые платформы

Основная аппаратная платформа:

- ESP32.

В дальнейшем должна сохраняться возможность перехода на:

- ESP32-S3;
- ESP32-C6;
- другие совместимые микроконтроллеры.

---

# 14. Долгосрочная стратегия

Проект рассматривается как единая программная платформа.

В дальнейшем планируется разработка:

- контроллеров телевизионных лифтов;
- контроллеров автоматических штор;
- контроллеров мебели;
- контроллеров ворот;
- контроллеров освещения;
- контроллеров вентиляции;
- универсальных модулей ввода-вывода.

Все устройства должны использовать общую архитектуру, единый стиль разработки и максимально возможное количество повторно используемых модулей.

---

# 15. Критерии успеха проекта

Проект считается успешным, если:

- устройство стабильно работает в течение длительного времени;
- обновление прошивки выполняется без участия пользователя;
- первоначальная настройка занимает не более нескольких минут;
- добавление новых функций не требует изменения существующих модулей;
- новая аппаратная ревизия поддерживается с минимальными изменениями программного обеспечения.

---

# 16. Основной принцип проекта

**Надежность важнее функциональности.**

Любая новая возможность должна добавляться только в том случае, если она не снижает надежность, безопасность и сопровождаемость системы.

---

# 17. Основные сценарии использования (Use Cases)

## Сценарий 1. Первое включение устройства

1. Пользователь подает питание.
2. Контроллер выполняет самодиагностику.
3. Проверяет наличие сохраненной конфигурации.
4. Если конфигурации нет:
   - запускает собственную точку доступа Wi-Fi;
   - автоматически открывает страницу первоначальной настройки (Captive Portal).
5. Пользователь выбирает тип подключения:
   - Wi-Fi;
   - Ethernet.
6. После сохранения параметров контроллер перезагружается.
7. Выполняется подключение к сети.
8. Контроллер регистрируется на сервере.
9. Устройство готово к работе.

---

## Сценарий 2. Обычная работа

1. После включения устройство автоматически подключается к сети.
2. Проверяет наличие новой версии прошивки.
3. Переходит в рабочий режим.
4. Выполняет команды пользователя.
5. Передает диагностическую информацию.
6. Контролирует состояние оборудования.

---

## Сценарий 3. Потеря сети

1. Контроллер обнаруживает потерю соединения.
2. Продолжает управлять механизмом локально.
3. Периодически пытается восстановить соединение.
4. После восстановления автоматически синхронизируется с сервером.

---

## Сценарий 4. Смена Wi-Fi

1. Контроллер не может подключиться к сохраненной сети.
2. Выполняет несколько попыток подключения.
3. Если подключение не удалось:
   - запускает режим первоначальной настройки.
4. Пользователь вводит новые параметры сети.
5. Настройки сохраняются.
6. Контроллер автоматически подключается к новой сети.

---

## Сценарий 5. Обновление прошивки

1. Контроллер проверяет сервер обновлений.
2. Если доступна новая версия:
   - скачивает прошивку;
   - проверяет контрольную сумму;
   - записывает новую прошивку во второй OTA-раздел.
3. Выполняется перезагрузка.
4. Если новая прошивка успешно запустилась — она становится основной.
5. Если запуск завершился ошибкой — выполняется автоматический откат.

---

## Сценарий 6. Отключение питания

1. Питание пропадает.
2. После восстановления питания контроллер автоматически загружается.
3. Восстанавливает сохраненную конфигурацию.
4. Подключается к сети.
5. Возвращается в рабочий режим без участия пользователя.

---

## Сценарий 7. Управление устройством

Пользователь может управлять устройством:

- локальными кнопками;
- мобильным приложением;
- веб-интерфейсом;
- REST API.

Независимо от способа управления логика работы устройства должна быть одинаковой.
